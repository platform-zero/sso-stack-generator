# Existing-host integrated test venue — preflight contract (not an installer)

`ops/verify-existing-host-venue.py` is an **offline/read-only, fail-closed path, identity and rendered-Quadlet screen** for a proposed selector; its output always includes `activationAuthorized: false`. The complete 60-module/95-service selected composition has 65 volumes: 61 explicit `hostPath`s and four implicit Huly volume names (`huly_cockroach`, `huly_elastic`, `huly_minio`, `huly_redpanda`). The 61 explicit paths must match the generated IR byte-for-byte; the four implicit Huly destinations must be exactly the named-volume `_data` paths inside the generated, exclusively owned apps graph, not invented independent bind paths. Selector user/UID/subid/state/graph/volume roots must match the generated domain manifest. The tool refuses existing paths even when empty, overlapping paths, protected bind ancestors/descendants, symlinked ancestors, duplicate accounts/UIDs/subordinate ranges, unbound domain roots, unit-prefix reuse and incomplete/colliding port proposals. For the selected bundle, the host CLI enumerates all 45 Quadlet `PublishPort` declarations plus Caddy 80/443 and node-exporter 9100 (48 unique required identities), and reads live account/subid/socket tables. The rendered-Quadlet screen now rejects original `webservices-*` unit/network/container identities, host-network containers without separate listener proof, escaped bind sources (including unmodelled generated config/log/socket/runner binds), writable host OS readers, implicit Huly volumes outside the apps domain, and published ports not equal to the exact 45 non-ingress proposed mappings. The updated private dirty site draft now passes all 194 unit identities, 12 rootful store-unit bindings and all 45 proposed published-port mappings. Its historical 224 rendered mounts had no unclassified source; the newer venue-only `volume-init` safety change removes six broad writable mounts and adds one exact root-private ready-marker reader (219 current mounts). The guarded `volume-init` refuses to start until a separately reviewed host installer creates that marker after verifying the actual domain-owned data paths/ACLs; it never runs the legacy blanket chmod/chown script. The current 219 mounts have no unclassified source after binding the site-declared new storage, control-socket and Caddy log roots, moving the two module test-runner bind sources and CI-runner SSH source, and retaining four named Huly volumes in the apps graph. It still **fails** the five host-network Quadlet checks and is not activated. Source-level mount rewrites do not install a second control service, prove private ingress/DNS/CA/mail, or configure the non-Quadlet test-runner script, installer and rollback consumers. Caddy 80/443 and node-exporter 9100 plus the other host-network consumers still need dedicated endpoint and actual ingress review; static port coverage alone does not prove runtime wiring. Its 76-row inventory input is a **protected-set supplement**, not fresh proof of all actual writers.

**Do not pass a selector to the current `install-podman-bundle.sh --activate` and assume isolation.** That installer still uses the production `webservices-*` system and user unit names, selected seven existing account homes, production `/etc/containers/systemd`, `/etc/systemd/system`, `/run/webservices`, `/var/log/webservices`, `/usr/local/sbin/webservices-auto-update`, rootful Podman defaults and existing rootless storage configuration. It enables/restarts those units, writes environment and storage configs, updates selections, and may copy/chown/ACL selected volume trees. Merely redirecting `WEBSERVICES_STATE_ROOT` or changing 61 volume host paths is unsafe. Do not run the native activation or reset on the physical host yet.

An unselected generator branch can now take paired site settings `podman.unit_prefix: p0test-…` and `podman.rootful_state_root: /var/lib/p0test-…`; with explicit `podman.rootful_graph_root` under the new test SSD tree and `/run/<prefix>-podman` `podman.rootful_run_root`; it emits separately named Quadlets, containers, networks, environment roots, rootful release binds and a `podman-domains.json` venue binding. Each rootful container/build/network Quadlet also declares an isolated `CONTAINERS_STORAGE_CONF` path under the new state root; the rendered preflight requires that binding on every rootful Podman unit. Image preparation now refuses a venue unless the exact dedicated rootful graph, runroot and `0600` root-owned storage configuration already exist; once present it uses both that config and explicit Podman `--root`/`--runroot` for rootful image import/pull/inspect, while unsetting the rootful storage override on rootless calls. **That configuration is not yet provisioned by a versioned installer, nor are all other installer/maintenance/rollback commands routed through it; no real graph isolation or install authority follows from these checks.** A complete `podman.port_map` of 48 old→proposed host-port identities also drives 45 published listeners, cross-domain endpoint rewriting, generated Caddy upstream loopbacks and the endpoint firewall; original↔rendered mapping is emitted in the venue metadata and independently compared to the selector. An isolated `p0-venue-*` guest VM spec must have a distinct name equal to `<network>-agents`, an exclusive disk root `/mnt/lab_debian/agent_vm/<name>` (never original `clean-role`), bind its HTTPS/IMAP/SMTP connect ports byte-for-byte to the generated site port map, and use a compatible clean controller. The separate venue selector's proposed guest network, address/gateway, port tuple and clean controller commit must match those rendered guest inputs before any Quadlet screen. This is source authority only, not a working bridge, resolver or controller. This does **not** rewrite Caddy's own 80/443 listeners, host-network consumers or all module-specific embedded ports. A read-only `ops/render-existing-host-guest-network.py` can also derive proposed libvirt NAT/isolated DNS XML from the guest selector, site VM spec and all 52 Caddy domain aliases. Its `--inspect-host` mode refuses an overlapping live IPv4 route, existing libvirt network name or existing bridge interface; the XML is schema-validated only, **not** defined/started or ingress-tested. For the selected venue-only high ports, the source renderer now builds Caddy global options `default_bind 127.0.0.1`, `http_port 56045`, `https_port 56042`, `auto_https disable_redirects`, and `servers { protocols h1 h2 }` directly from the site port map; it rejects ACME mode or a sealed-input listener override. This is **not** proof of a running Caddy listener: a reviewed guest-bridge-only TCP ingress relay (including standard 443 for existing OIDC URLs), live wildcard/UDP listener checks and HTTP redirect replacement remain required. The venue generator also rewrites the single Caddy device-API upstream from the old original guest `.235:24838` to the exact new guest's site-owned private `.115:24838`, refusing any changed source block or guest network. The Caddy control Unix path remains `/run/p0-control/http.sock` **inside the container** but its Quadlet source mount is exclusively `/run/p0test-r1-control`; this must be verified alongside a separate host-controller lifecycle before activation. The new guest controller must pin its device service to its own private address before it starts. `ops/render-existing-host-ingress.py` proposes, but never installs, a guest-bridge-only socket-activated TCP relay on 443 and the mapped HTTPS port, both directed **only** to Caddy's loopback high port. It binds to the guest network device and the versioned rootful Caddy unit; its install target is the isolated stack target, not the global sockets target. Port 443 is required because existing OIDC issuer URLs and callbacks use standard HTTPS; an isolated port map alone does not change client URLs. It refuses mismatched guest, Quadlet, TLS and storage authority. The proposed units pass offline systemd syntax checks with synthetic dependency stubs, not a runtime TLS/ingress proof. `ops/render-existing-host-mail-ingress.py` separately proposes bridge-only SMTP/IMAP TCP socket relays for the standard and mapped guest ports, targeting **only** Mailserver's four proved loopback publishers; port 25/465 remain loopback without a guest relay. The mail proposal explicitly says `mailTlsProved=false` and `mailSinkProved=false`. `ops/render-existing-host-guest-fence.py` proposes a dedicated nftables table bound to both verified proposals: guest bridge input is limited to private DNS/DHCP, SSH, Caddy TLS and narrowly approved SMTP/IMAP ports; other host destinations and IPv6 are denied, RFC1918 forwarding is denied, and physical-interface access to those bridge sockets is denied. Unrelated host tables remain unchanged. Hostile fixtures and `nft -c` syntax verification are source-only. Optional root-only `scripts/test-existing-host-guest-fence-live.py --proposal ROOT_PRIVATE_JSON` tests the proposed rules using **disposable network namespaces only**: narrowly allowed guest ports work, a deliberately bound internal publisher/admin port and non-bridge HTTPS/private DNS ingress and a reachable RFC1918 forward target are denied, and the real host bridge/table are absent before and after; a hostile early-publisher-accept fixture fails the packet check. Host nft counters may change independently under production traffic, so a whole-ruleset checksum is not a reliable no-mutation proof. This does not prove the actual libvirt bridge. Atomic fence installation **before** network/guest startup, real firewall ordering, dynamic listener inspection and exact scoped teardown remain unsatisfied. The next local candidate explicitly pins Alloy's HTTP/UI listen option to `127.0.0.1:12345`; `ops/verify-existing-host-listener-intent.py` separately classifies exactly four remaining rootful host-network units (Alloy, Caddy, node-exporter and ntfy native-auth), refusing wildcard flags, an unexpected unit or a host-network publisher. The venue preflight additionally treats 9100/12345/25017 as actual local listener reservations rather than crediting unused Podman port remaps. The venue-only Caddy global options disable its default unauthenticated localhost admin API, avoiding a control-plane bypass from other host-network consumers; a real pinned-image adaptation and live health check must prove that separately. These are static and point-in-time read-only checks: they neither justify starting the units nor prove what the real processes eventually bind. The next local candidate requires three additional disjoint Livekit port identities: the SFU HTTP API is loopback-only for Caddy, and the RTC TCP/UDP sockets are explicitly bound to the private guest gateway and mapped ICE-advertised high ports. Both generated and natively re-rendered Livekit config bind the ICE node/ports to site authority, not the old LAN IP; the guest fence refuses a host-network or wildcard Livekit Quadlet. RTC is not claimed as Caddy-authenticated HTTP: Livekit's token and DTLS/ICE controls, rootless bridge publisher behavior and device-bound nftables must be proved live before enabling it. An explicit venue-only Caddy HTTP site now returns 308 to `https://{host}{uri}` without leaking the internal high port; a separate proposed bridge-only 80/mapped-HTTP socket forwards to Caddy loopback 56045. The pinned Caddy image must still adapt both HTTP and HTTPS listeners solely on loopback, and a real guest browser must demonstrate the redirect without wildcard publication. Mailbox/broker exposure and external guest egress remain separate gates. The generator also remaps the four Mailserver 25/465/587/993 listeners onto **host loopback only** for this synthetic venue. Earlier proposed bundles had wildcard publishers at four high ports; they must never be activated. The venue verifier now rejects even one non-loopback published port. Proposed mail TLS/IMAP relays for the guest are separate from the Caddy-only HTTPS socket and require TLS service-name, auth and synthetic mail-sink checks before install. All 45 published listeners stay on host loopback, never directly on the guest-facing bridge. The preflight requires exact selector↔generated unit/state/runtime/graph/port agreement; an old bundle without the new venue metadata refuses. This is **not** an installer: the current installer still uses fixed production targets/storage and the new branch deliberately fails the host-network, old explicit runtime/mount and unremapped port screens. Do not activate merely because the 194 generated Quadlet names are distinct.

A supported **versioned** venue implementation must consume an exact provenance-bound selector, transform the selected site/generator runtime and all service references (including implicit Huly binds), and prove exclusive accounts/subids, graphroots, units, sockets, ports, DNS/CA/mail sink and ownership from the rendered Quadlets before any installer mutation. Separate native unit/timer/target names, rootful and seven rootless image stores and all unit-scoped runtime directories are necessary while original production runs. Review image preparation/build targets, host control and guest broker endpoints, restart/healthcheck triggers, network namespaces and public Caddy ingress. Stop and reset only positively identified test-owned names/paths, checking other consumers and libvirt UUIDs. Do not use prune or delete any existing bind contents. Revalidate the physical reserve and live graph immediately before activation; selector preflight alone cannot grant stop, reset, apply or test authority.

`python3 -B scripts/test-existing-host-venue.py` exercises adversarial source fixtures, including escapes in generated Quadlets despite valid IR. These are not a native install, live graph-closure proof or a coupled host/guest test.
